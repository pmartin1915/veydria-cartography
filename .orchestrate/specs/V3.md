## Sub-item A — Markdown export: trim default party to active-party size

**Goal:** When the journey planner exports to markdown, the party list should only show
the active-party members, not all 6 slots (most campaigns have 3–4 members; 6-slot export
pads with empty entries).

**Locate:** Grep `web/src/` for `campaign-log` or `markdownExport` or `exportToMarkdown`
to find the current export function. Also check `JourneyPlanner` for any export handler.

**Desired behavior:** The exported markdown shows only the non-empty party slots. Empty
slots are not exported. The export should not change the journey state.

**Acceptance:** Add or update a test in `web/src/utils/` or `web/src/components/` asserting
that the markdown export of a 3-person party does not contain empty party-slot placeholders.

## Sub-item B — Comparison card: party-cost tooltip

**Goal:** The comparison card (the UI element that shows route alternatives side by side)
should show a tooltip or label for the party cost column, so users know what the cost
represents (rations, water, days — whichever is the comparison metric).

**Locate:** Grep `web/src/` for `ComparisonCard` or `comparison-card` or `JourneyPlanner`
to find the component. Look for where party cost is rendered.

**Desired behavior:** A `title` attribute or a `<Tooltip>` wrapper around the party-cost
value that explains what the number means (e.g., "Party cost: 3 rations + 2 days"). The
exact label text can match whatever units are shown elsewhere in the UI — be consistent.

**Acceptance:** The tooltip/title attribute is present in the rendered output. No existing
tests should break.

---

## Sub-item C — Time-of-day wiring in encounter generation

**Goal:** `generateEncounters` (or equivalent) should accept and use a time-of-day parameter
to influence which encounters are generated (e.g., nocturnal encounters at night, desert heat
penalties at midday). Currently it may ignore the time-of-day entirely.

**Locate:** Grep `web/src/` for `generateEncounters` to find the function. Check its
current signature and whether it has a time-of-day parameter.

**Desired behavior:** If time-of-day is not yet a parameter, add it as an optional parameter
with a sensible default so existing callers don't break. If it's already a parameter but
ignored, wire it into the encounter-selection logic (at minimum, filter out encounters
tagged for incompatible times-of-day).

**Acceptance:** A unit test in the nearest `*.test.ts` file verifies that calling
`generateEncounters(...)` with `timeOfDay: 'night'` returns encounters appropriate for
nighttime (or excludes daytime-only encounters), and calling with `timeOfDay: 'day'` returns
the opposite. If the encounter data has no time-of-day tags yet, add tags to at least 2
encounters as the data sample.
