if the party encounters "ford" twice in a journey, both encounters show identical text.

narrative/label set than the first.

dramatic beat that currently goes through the generic encounter path).

## Part 1 — Per-instance variation (plumbing only)

**The structure change:**  
Change `SIGNATURE_CHOICES` from `Record<string, EncounterChoice[]>` to
`Record<string, EncounterChoice[][]>` — an array of VARIANTS per key. Index `[0]` is the
first-encounter set, `[1]` is the second, etc. If the instance index exceeds the variants
array length, wrap around (modulo) or use the last variant.

**`signatureForDay` must track encounter count by key:**  
The function (or its caller) needs to know how many times each signature encounter key has
been resolved in the current journey. Add a `signatureCounts: Map<string, number>` to
`JourneyState` (or pass it in from the caller), increment it each time a signature encounter
is resolved, and use it to index into the variants array.

**⚠️ Prose is Perry's responsibility:**  
For keys that currently only have 1 set of choices (`ford`, `bandits`, etc.), leave the
existing choices as `variants[0]` and add a `// TODO: add variant prose for instance 1+`
comment placeholder. Do NOT invent or generate variant prose text. The prose will be
supplied by Perry in a follow-up session.

**Type compatibility:**  
Any component or function that currently reads `SIGNATURE_CHOICES[key]` (type
`EncounterChoice[]`) must be updated to read `variants[instanceIndex]` (type
`EncounterChoice[]` still — the inner array type is unchanged). Do NOT change `EncounterChoice`.

## Acceptance criteria

1. `SIGNATURE_CHOICES` type is `Record<string, EncounterChoice[][]>`.
2. Repeated resolution of the same signature key within one journey produces different
   `EncounterChoice[]` arrays (variant 0 vs. variant 1, etc.) — or the same variant if only
   one variant exists.
3. All existing callers of `SIGNATURE_CHOICES` still compile (typecheck passes).
4. At least one encounter in `encounters.ts` has been promoted to a signature encounter
   (has a `key` field and a corresponding `SIGNATURE_CHOICES` entry).
5. `cd web && npm run test` passes (≥908 baseline).
6. `cd web && npm run build` passes.

**New unit tests** (add to `web/src/utils/passage.test.ts`):
- Test that a journey with two "ford" encounters resolves to `variants[0]` on the first and
  `variants[1] ?? variants[0]` (wrap-around fallback) on the second.
- Test that a journey with only one encounter of key X always gets `variants[0]`.
